What changed vs. the first pass: removed the permanent left "Elements" column and right "Properties" column — Squarespace never boxes the canvas in with dense panels. Adding content happens contextually (hover seam → "+" → visual gallery of section layouts) instead of dragging generic blocks from a palette. Editing a section's look happens via a small floating toolbar anchored to that section, and text is edited in place with a lightweight formatting pill — not a sidebar full of input fields. Global look-and-feel (fonts, color palette, spacing/shape) is consolidated into one "Design" panel reached from the icon rail, so style decisions happen in one predictable place instead of being repeated on every element. The code escape-hatch still exists (rail + advanced CSS in the Design panel) but is deliberately tucked away rather than front-and-center.
Decided this round: quick per-section overrides (background, padding, corners, per-breakpoint visibility) live in a small popover off the gear icon — state 5 above — so the common 80% case never requires leaving the section you're looking at. A Layers panel is included (state 15) — see reasoning below. "Smart suggestions" in the Add-section panel is sketched as an off-by-default toggle rather than the default browsing mode — see reasoning below.
New — Advanced panel redesign (states 6–10, 2026-08-17, supersedes the earlier "…" popover): the old "more" popover for Layer 2 block properties is replaced with a real panel: it docks as a right-hand column by default (state 7, auto-opens on selection), falls back to showing Page Settings instead of going blank when nothing is selected (state 6 — a gap in the original design), and can be set per-account to only open on request (states 8–9, via the new "Advanced …" pill on the direct controller) rather than always auto-opening — see the new Account Settings tab. On a narrow editor window it always presents as a slide-in overlay with a scrim behind it, regardless of that setting, since a permanent docked column would crowd the canvas at that width (state 10). The lightweight per-section popover from state 5 is unaffected — it still handles the common quick-override case without invoking the full panel.
Why Layers works this way: it's opened from the rail exactly like Add and Design — an on-demand overlay that slides in over the canvas and disappears when you're done, never a permanent third column. That's the difference that keeps it from reintroducing WordPress-style clutter: it's there when a power user needs to jump to something the hover/click method can't easily reach (an element hidden behind another, a deeply nested block, reordering three sections at once), but it's invisible to everyone else by default and doesn't compete with the canvas for space. Rows mirror the actual section order top-to-bottom, so it also doubles as a quick page outline.
On AI-suggested layouts and cost: yes — this has real, ongoing cost implications, unlike the rest of the UI which is basically free to run. Every "smart suggestion" is a live model call (roughly: page context in, ranked layout list out) that costs money per use and scales with usage, not a one-time build cost. It's also different in kind from picking off a static category grid, which costs nothing to run no matter how many users click it. The wireframe reflects that: smart suggestions are sketched as an explicit, off-by-default toggle, so the flat category browser (state 13) stays the default, free, and instant path, and AI ranking is something a user opts into. Worth deferring a final call on pricing/limits until there's real usage data.
Animate (state 11): a ✨ icon on the floating toolbar opens a click-to-apply preset grid (Fade in up, Fade in, Slide in left/right, Zoom in, None) — no keyframe editor, no timeline, matching the "click text to edit" directness of everything else in Layer 1. Two secondary controls (when it starts, how fast) cover the realistic range of what a non-technical user wants without turning it into a motion-design tool. This sits at the Layer 2 tier conceptually — additive polish, never required to publish a page.
Developer mode (state 12): now shows two things at once, reflecting that they're independent settings — the docked bottom panel with raw custom CSS for the block (unchanged from the earlier pass), and the same Advanced panel used in states 6–10 with an extra "Developer (Layer 3)" section appended for custom code and absolute positioning. The Advanced panel display setting (Always / Only when I open it) still governs when that panel shows up; Developer mode only changes what's available once it's open.
Purpose: the "streamlined design-system approach" the concept calls for — one place to manage colors, type, spacing and reusable patterns as variables/tokens, instead of WordPress's scattered theme.json / Customizer / block-style panels.

Aligned to Flow 9 / security model (resolved 2026-08-17 in the flow doc): visitor-facing code (widgets, embeds, animations) installs immediately after the automated scan shown in state 2 — no manual review queue, since that would recreate WordPress-style plugin-approval friction. Anything requesting editor/dashboard access always goes through the sandboxed permission prompt in state 3, with no exception, because that surface has session cookies and account-level API access — the same reasoning browser extension stores use.
Still open: a public marketplace (installing plugins other users authored) is a different trust model — manual review, versioning, and code signing — and isn't needed for MVP's single-user/small-team scope. Tracked in claude/open-decisions.md since it affects how much the sandboxing architecture should anticipate now, even though the feature itself would ship later.

Lives in Account Settings, outside the builder, and applies across every site the person edits — not per-site. Two independent controls: when the Advanced panel shows up while editing (Page Builder states 6–10), and whether Developer Mode's extra fields are unlocked at all (state 12).

Advanced panel

Controls when the advanced properties panel appears while you're editing a block. Separate from Developer mode below.

Opens the moment you select a block. Default — drives Page Builder states 7, 10 and 12.
Only show it when I open it
Keeps the canvas clear — click "Advanced …" on a selected block to open the panel. Drives states 8–9.

Developer mode

Unlocks custom code, absolute positioning, and custom breakpoints inside the advanced panel and the builder's bottom code panel. Off by default.
Independent of the Advanced panel setting above — turning this on doesn't change when the panel opens, it changes what's available inside it once open (see Page Builder state 12).
Judgment call flagged for confirmation (carried over from the v0.4 supplement): on a narrow editor window with nothing selected, the panel stays fully closed rather than auto-showing Page Settings as an overlay — reasoned that an unrequested overlay covering the canvas on load would be intrusive at that width, so Page Settings is reached via the rail icon instead.
