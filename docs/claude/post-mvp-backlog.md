# Post-MVP Backlog

A running list of good ideas that came up while designing the MVP, deliberately deferred so the first version stays focused. Add to this list as new ones surface; revisit once the MVP is working well enough for real users.

**Scope note (added 2026-08-18):** this doc holds *features and capabilities deliberately pushed past MVP*. Decisions that need answering now — even if the feature they unblock ships later — live separately in `claude/open-decisions.md`. If you're not sure which list something belongs on, ask: "does this need a decision before/during MVP build, or is it a feature we're consciously not building yet?" The former goes to open-decisions, the latter goes here.

## Monetization / Paid Tiers
- **General direction (decided 2026-08-17):** the plan is free/MVP tier now, paid tier(s) later that unlock added features rather than raising the ceiling on the core editing experience. First concrete example: the animation preset set (Fade in up, Fade in, Slide in left/right, Zoom in, None — see Page Builder wireframe) stays fixed for now; a paid tier would later expand it with more animation options. Noting this now so future feature decisions get evaluated against "is this a free-tier core feature, or a paid-tier expansion" rather than each one being litigated from scratch.
- **Design implication to revisit:** once there's a second tier item beyond animations, worth deciding whether the wireframes should show a consistent "Pro" affordance pattern (e.g. a small lock icon or "Pro" tag on gated options) so upgrade prompts feel like one system rather than one-off treatments per feature. Not sketched yet — the animation panel currently shows only the free set with no visual hint that more exist, which is fine for now but will need a treatment once the paid tier is real enough to design against.
- **Related:** the "Smart suggestions" AI-ranked layouts feature (below, under Page Builder) is a strong second candidate for a paid tier, since it has real per-use cost unlike most of the editor.
- **Overall pricing model still undefined** — raised 2026-08-18 during a documentation review. Beyond the two feature-flag examples above, there's no sketch yet of tiers, storage limits, custom-domain costs, or (now that e-commerce is confirmed deferred, see Commerce section below) transaction fees. Given "expensive competitors" is the founding complaint in `The idea`, this deserves directional shape before it affects storage/metering architecture decisions.

## Dashboard
- **Team/role indicator per site card** — for multi-user agencies, show who has access and what role (owner, editor, viewer) directly on each site card without opening into the site. Raised 2026-08-17 while reviewing the Dashboard wireframe; deferred because the MVP's single-user (or small-team) use case doesn't need it yet, and it adds a decision (how are roles modeled? per-site or per-workspace?) that's easier to answer after the core team/permissions model exists. Note: MVP's small-team scope was made explicit 2026-08-19 (see `open-decisions.md` #10, resolved) as invite + shared billing only, no per-site roles — consistent with deferring this item.

## Page Builder
- **"Smart suggestions" for Add-section layouts** — AI-ranked layout suggestions based on page type/content, instead of the flat category browser. Raised 2026-08-17; deferred/sketched as an explicit opt-in toggle (off by default) because it's a live, per-use model-call cost that scales with usage, unlike the rest of the editor. **Scope expanded 2026-08-19** (see `open-decisions.md` #4, resolved): confirmed to also apply at the New Site starting-template step, not just in-editor "Add block" — same AI-ranking logic, second entry point, so the cost/pricing model decision below now needs to account for two call sites instead of one.
- **AI suggestions — cost/pricing model decision.** Raised 2026-08-17. Each smart suggestion is a live model call (page context in, ranked layouts out), so cost scales with usage rather than being a one-time build cost — unlike the flat category browser, which is free to run no matter how many users click it. Before turning this on by default or promoting it, decide the cost model. Options to weigh once there's real usage data:
  - Small free quota (e.g. a few suggestions per site or per month)
  - Gate behind a paid tier
  - Cache/pre-rank suggestions for common page types (restaurant, portfolio, real estate, etc.) to cut per-call cost at scale
  - Usage-based metering passed through to the user, if margins require it
  Needs real usage numbers before committing — premature to price this off assumptions. **Related decision (2026-08-19):** the separate but related question of cost control for "Build from a prompt" (the New Site onboarding AI feature) was resolved in `open-decisions.md` #5 — a free quota per new account, rather than the off-by-default toggle used here, because it's the core onboarding hook rather than an in-editor nice-to-have. The two features' cost models were deliberately decided to differ; see #5 for the reasoning.
- **Expanded animation library (paid tier)** — more presets beyond the free set (e.g. combinable effects, custom timing/easing, staggered animations on card groups). Raised 2026-08-17 as the first named paid-tier feature; see Monetization section above.
- **Version history / rollback** — raised 2026-08-18 during a documentation review. No doc currently describes anything beyond autosave ("Saved 2s ago"); there's no revision history or recovery-from-a-bad-edit story, which WordPress, Webflow, and Squarespace all treat as table stakes. Flagging as backlog rather than an open decision because it's a build-scope call (whether it ships in MVP at all), not a definitional question — but worth revisiting soon since it affects the underlying data model (deltas vs. snapshots vs. current-state-only) and is cheaper to design for now than to retrofit.

## Collaboration & Permissions
*(New section, 2026-08-18 — consolidates items previously scattered across `user-flows-v1.md` and the wireframe notes as inline "deferred" mentions that hadn't actually been logged here.)*
- **Multi-user simultaneous editing** — live co-editing (Google-Docs-style) of the same site/page by more than one person at once. Explicitly out of scope for MVP per `user-flows-v1.md`'s flow inventory; MVP targets single-user/small-team use without simultaneous editing. Confirmed again 2026-08-19 when MVP's small-team scope was made explicit — see `open-decisions.md` #10 (resolved).
- **Per-site role permissions** — owner/editor/viewer roles scoped to individual sites. Also explicitly deferred per the flow inventory, and confirmed out of MVP scope again via `open-decisions.md` #10 (resolved 2026-08-19). Related to the Dashboard "team/role indicator" item above — likely worth scoping together.
- **Publish conflict/lock state** — what should happen if a user publishes mid-edit from another device or browser tab? Raised in `user-flows-v1.md` Flow 8 as "not previously logged" and flagged for this doc, but wasn't actually added until now. Worth noting this can happen even for a *single* user with two tabs open, so it may be more MVP-relevant than "collaboration" framing suggests — worth a second look before assuming it's safe to defer entirely.

## Design System
- **Team-shared token library (agency use case)** — added 2026-08-18, alongside the decision (see `open-decisions.md` #6, resolved) to scope design tokens per-site only for MVP. One token library backing multiple sites for the same team, with per-site override capability, would serve agency users well but adds real complexity (library versioning, per-site overrides) that's easier to design once the team/permissions model itself exists. Revisit once that model is in place.

## Commerce
*(New section, 2026-08-19.)*
- **E-commerce (product blocks, cart, checkout) — confirmed deferred to post-MVP (decided 2026-08-19).** See `open-decisions.md` #11 (resolved) for the decision record. Resolves the "is this in MVP at all" question — it isn't — but leaves the actual design question open for whenever it's picked back up: is e-commerce a Layer 1 default block type (product/cart/checkout as ordinary blocks, keeping the "everything is a block" mental model simple) or a separate mode entirely (more accurate to how commerce actually works — inventory, checkout state — but more architecturally distinct from regular pages)? Also ties into the Monetization section above once scoped, since transaction fees are a plausible revenue lever.

## Plugins
- **Public plugin marketplace — confirmed for post-MVP (decided 2026-08-19).** Users will be able to install plugins authored by other users/developers, not just their own uploads. See `open-decisions.md` #12 (resolved) for the decision record. Not building this for MVP, but it's a committed direction, not a maybe — which matters because it changes what the MVP's plugin sandboxing architecture (iframe isolation, permission manifests) needs to anticipate now, even though the marketplace itself (review flow, versioning, code signing, discovery/listing UI, revenue share if any) is built later. Concrete follow-ups once this is picked up:
  - Trust/review model: manual review queue (similar to browser extension stores) vs. automated scanning vs. hybrid
  - Versioning and update distribution for installed plugins
  - Code signing to prevent tampering post-review
  - Whether there's a revenue share / paid-plugin model (ties into Monetization section above)
  - Discovery/listing UI — likely a new Dashboard surface. Related to `open-decisions.md` #9 (Templates nav, resolved 2026-08-19 as its own Dashboard nav item): both are "does this need a new top-level nav destination" questions, and it may be worth designing the two nav additions together rather than one-off.

## Accessibility
*(New section, 2026-08-19.)*
- **Full editor keyboard/screen-reader pass — deferred to post-MVP (decided 2026-08-19).** See `open-decisions.md` #14 (resolved) for the full decision record, including the research behind it (WAI-ARIA has no official drag-and-drop pattern; WordPress Gutenberg is the closest real precedent) and the MVP baseline that *is* in scope now (keyboard block selection, panel-based editing as the non-drag equivalent, keyboard-triggerable "Add block," and basic ARIA labeling). What's specifically deferred here, beyond that baseline:
  - **Navigation mode / outline list view** — a Gutenberg-style way to Tab through blocks like headings in a document, or see an outline-like hierarchy of blocks, rather than relying on canvas-order Tabbing alone. Meaningfully improves the experience for complex pages but isn't required for a baseline non-mouse path to exist.
  - **Dedicated reorder keyboard shortcuts** — a fast "move this block up/down" shortcut (Gutenberg's model: Ctrl+Option+Arrow / Shift+Alt+Arrow), as an alternative to manually editing X/Y numbers in the Advanced Panel for simple reordering.
  - **Full WCAG 2.1 AA screen-reader pass across the whole canvas** — the MVP baseline covers basic labeling on blocks/panel; a full pass (live-region announcements on state changes, complete semantic structure, testing with real screen reader software) is real, ongoing work best done once the canvas UI is stable rather than mid-design-churn.
  Worth revisiting soon after MVP ships rather than letting it linger — this was flagged once already (project review, 2026-08-18) as a gap that went unaddressed for a full doc-review cycle before finally getting resolved.
